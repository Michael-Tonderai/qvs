# requirements.txt
#
# Runtime dependencies. Installed in the local .venv, in CI, and in the Docker image.
#
# Version ranges rather than exact pins: compatible-release ranges keep security
# patches flowing without a dependency-update workflow that this project has no time
# to run. A full lockfile (pip-tools, uv) was considered and rejected as
# disproportionate for a six-week deliverable - see D-016.
#
# gunicorn carries an environment marker. It is the production WSGI server used
# inside the Linux container, and it neither installs cleanly nor runs on Windows.
# The marker means one requirements file serves all three environments rather than
# splitting dependencies across files that then drift apart.

Django>=5.2,<5.3
gunicorn>=23.0,<24.0; sys_platform != "win32"

# whitenoise serves static files from the application process. Django deliberately
# stops serving them when DEBUG is off, and the container runs with QVS_DEBUG=0, so
# without this the admin renders with no stylesheet - which reads as a broken system
# in the demonstration video rather than as a scoped-out feature.
#
# Rejected: a separate nginx container. That is the correct answer for a production
# deployment and the wrong one here, because it doubles the compose file, adds a
# service to explain, and buys nothing an assessor is looking for. The trade is a
# sentence in the report's critical evaluation.
#
# No platform marker: whitenoise is pure Python, installs on Windows, and is needed in
# the local .venv so that a QVS_DEBUG=0 run behaves the same locally as in CI and in
# the container - the parity D-010 is about.
whitenoise>=6.7,<7.0
